# Brownfield adoption

Use this route when existing implementation constrains the requested behavior
and authored coverage is missing, partial or conflicting. Locate the selected
workspace with [bootstrap](workspace-bootstrap.md). Inspect governing contracts,
actual entrypoints, tests, executable config and direct dependents.

Separate observed behavior, intended contract, historical documentation, confirmed
defects and unknown intent. Code alone does not establish what the product should
do. Resolve material conflicts from evidence or the user before dependent edits.

Inspect configured root/member boundaries without inventing members from directory
shape. Keep boundary summaries small and task-focused. Model each material owner
as a component with colocated expands; preserve accessible provider identities.
Do not generate a contract per file or copy implementation mechanics into prose.
For UI work, inspect routes, shared state and async behavior using
[frontend surface review](frontend-surface-review.md).

Write scoped authorized contracts and reconcile relevant ownership comments.
Use `sigil check`, then [native Design review](design-compilation-review.md) with
current independent reconstruction. Keep focused native membership and final
whole-task scope distinct. Adopt implemented native inspection, scope, freshness
and comparison instead of retaining duplicate temporary mechanisms.

During deletion, remove intentionally obsolete backend concepts and UI dedicated
to them. Preserve required language and native compilation/status behavior and
verify its actual integration. Deleting retained functionality to avoid integration
or retaining an obsolete API through an adapter both miss the refactor objective.

Continue [implementation design](implementation-design.md) and check actual
behavior, dependents and removals. A passing build or a native semantic warning
state does not establish complete delivery.
